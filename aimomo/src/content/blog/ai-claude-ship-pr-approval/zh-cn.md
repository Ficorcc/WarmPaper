## 一、11 月 23 日发生的事

Anthropic 发布了 Claude Ship，目前是 beta。一句话概括：它能让 Claude 看你的 pull request、把它修好，并在团队自己定的规则允许的情况下，直接批准这次改动。

面向的是 Claude Team 和 Enterprise 客户，跑在 GitHub 上，不强制要求你用 Claude Code。符合条件的企业组织还能领至少一万美元的 Ship 额度，30 天内用完，2027 年 1 月 15 日前领取。

这条新闻在技术圈的热度不算炸裂，但我觉得它比任何一次模型跑分提升都重要。原因很简单：过去两年，AI 一直在做"写"的活——写代码、写文案、写测试。而"审批"从来被认为是人类必须亲自守着的那道门。

现在这道门上装了一个电子锁，钥匙是仓库里的一个策略文件。

## 二、三个角色，最敏感的是第三个

Claude Ship 不是一个单体工具，它拆成了三个智能体：

**Code Review** 已经正式可用，对 PR 做多角度深度审查，先收集问题，再对抗性地自我验证一遍，分类后贴到 PR 上。每个仓库可以选 Quick、Standard、Deep 三档审查深度。

**PR Steward** 负责"让 PR 保持绿色"。CI 挂了、有合并冲突、有人提了意见，它去改。但它被明确设计成不能批准、不能合并——这个边界划得很清楚。而且它每次推送都会留言说明改了什么、怎么撤销；你可以随时 `@claude stop` 让它停手。

**Claude Approvals** 才是真正的变量。它读取团队写在仓库里的审批策略文件，决定这次改动能不能自己批。官方说它"像一个更聪明的 CODEOWNERS"，可以在决策时参考 Code Review 的结论，也可以参考团队用自然语言写的分类器。

## 三、为什么这一步比以前都敏感

代码评审这件事，从来不只是找 bug。它是一个责任分配机制：谁点了那个绿色按钮，出了问题谁解释。

以前的自动化工具最多做到"帮你检查"，最后的判断权和落笔权在人手里。Claude Approvals 把落笔权也接了过去——当然，是在人类事先写好规则的前提下。

我注意到官方文档里有两个细节，说明 Anthropic 自己也知道这一步很重：

一是建议大多数客户先用 observe-only 模式跑一段时间，只观察 Claude 会批什么、不会批什么，建立信心之后再改分支保护规则，要求必须有 Claude Approvals 的绿灯才能合并。

二是它和现有分支保护、必须通过的检查是共存的，不是替代关系。也就是说，你可以让它只负责一部分例行改动，剩下的还是走人工。

这套设计思路是对的。审批权这种权力，不该一次性交出去，而应该是先让 AI 在旁边看你批一万次，再让它在你划定的窄巷子里批几次。

## 四、他们自己是怎么用的

Anthropic 说 Claude Code 团队的大部分代码现在由 Claude 写。6 月到 9 月，合并的 PR 数量翻了一倍多，被回滚的比例下降了 40% 以上。

里面有个例子挺具体：有客户反馈 Analytics API 文档写错了，让人误以为 Admin key 能拉 Pro 和 Team 的用量。产品经理和 Claude 讨论完，Claude 自己开了 PR，Code Review 没发现阻塞问题，文档审查人签了字，Claude Approvals 通过，当天晚上就合并了。

这个故事有意思的地方在于：提需求的人、改代码的人、审查的人，三个角色里有两个不是人。剩下那个人只负责点头。

## 五、小团队真正能抄的是什么

Claude Ship 的定价和门槛决定了大多数独立开发者用不上它。但它背后的思路，完全可以抄：

**第一，把审批标准写成文件，而不是写在老员工脑子里。** 什么改动可以直接上，什么改动必须人看——如果这条规则你说不出来，说明它本来就不存在，你只是在凭感觉。

**第二，先观察后授权。** 想让 AI 参与任何有后果的决策，第一周永远应该是只读模式。看它判错几次、错在哪，再决定给它多大权限。

**第三，留好撤回路径。** PR Steward 每次推送都写"怎么撤销"，这是很成熟的工程习惯。自动化越强，可回滚性就越要当成硬指标。

## 六、我的判断

我认为 Claude Ship 真正卖的，不是"AI 会审代码"，而是"AI 可以承担签字责任"这件事的产品化。

它必然带来一个新问题：当 AI 批准了一个引入了安全漏洞的改动，谁该负责？Anthropic 的答案是——写策略文件的团队。这个答案法律上说得通，实践上却有点微妙：规则写得越宽松，出事概率越高；写得越严格，这工具就越没用，最后退回人工。

所以我的建议很朴素：把 AI 审批当成"给低风险改动的快速通道"，而不是"减少人头的手段"。真正需要判断力的改动——权限、支付、数据删除、对外承诺——继续让人类按手印。工具把例行的活接过去，人把不该出错的地方守住，这个分工才是稳的。

至于"AI 给自己写的代码签字"这件事本身，听着像左手签右手。但只要策略文件是人写的、审计日志留得住、回滚随时能做，这个闭环其实比很多团队现在"同事之间互相点个 LGTM"要严谨得多。
