你在 WordPress 后台点「安装」的那一刻，交出去的是什么？

是这个站点的数据库、文件系统、环境变量和网络出口。因为 WordPress 插件和站点跑在同一个 PHP 进程里，权限上没什么区别。这不是漏洞，是设计。一个联系表单插件，技术上完全有能力读你未发布的草稿、改另一个插件的代码，或者把数据发去任何地方。

绝大多数作者当然不会这么干。问题在于：**你信任的从来不是代码，是作者的自觉。**

我最近把 Cloudflare 的 Astro 原生 CMS——EmDash——的插件机制翻了一遍。它 9 月 28 日发布 1.0（MIT），10 月初连发 1.1、1.2。但插件架构值得看一眼：它把「信任」从人的层面挪到了代码层面。

## 换掉的不是 CMS，是权限模型

EmDash 1.0 的核心改动是插件默认跑在沙箱里。Cloudflare 上每个插件是独立的 Dynamic Worker；Node.js 上 EmDash 单独起一个 workerd 进程，每个插件在里面作为隔离服务运行。插件想要什么能力得自己声明，站长安装时逐项批准，**批准之后由运行时强制执行，不是写在文档里就算**。

权限粒度分得细：给文章建索引的插件能读内容、连搜索服务，但不能改文章、不能连其他主机；图片优化插件能管媒体，读不到用户内容；发布通知插件能观察发布动作并发邮件，改不了正在发布的内容。关键在于这些能力彼此独立——给了媒体权限，不等于同时暴露用户和未发布内容。

## 更值得琢磨的是插件从哪来

权限管住了运行时，但插件本身可不可信、来源能否验证？

EmDash 把「插件」和「目录」拆开了。发布者用 Atmosphere 账号发布，插件包和每个版本的记录由发布者自己签名，存在自己的账号里——底层是 AT Protocol（驱动 Bluesky 的那套去中心化协议）。registry.emdashcms.com 只是方便搜索安装的入口，不持有权威副本。

验证链条挺细：atproto 仓库用带签名的 Merkle 搜索树，一份包含证明能把某条发布记录连到发布者账号的一次签名提交，所以 EmDash 可以独立验证，不必相信目录里那份拷贝。插件在后台显示为 `@handle/slug`。若发布者 handle 无法解析回账号，EmDash 显示 INVALID HANDLE 并阻止新安装，**但已安装的站点保持原状**——身份查询失败不该把正在跑的站打死。

## 我的判断：该抄的不是 EmDash，是思路

EmDash 生态还很嫩。1.0 到 1.2 只隔九天，「注册表不归任何公司」这个主张完全没被规模验证过，默认服务仍是 Cloudflare 托管。短期内它撼不动 WordPress 的存量。

但它提出的问题是真的：**插件生态的安全，靠审核队列，还是靠架构？**

WordPress 选前者，数万插件排队靠人工和扫描筛，你永远在追赶。EmDash 选后者：默认不给权限、给就强制、来源自己验证，代价是生态起步慢。

作为自建站的博客作者，我现在能用上的不是 EmDash，而是这套思路的简化版：插件数量收敛；把「能发邮件、能连外网」的插件当高危，这类权限在共享进程里等于数据外流通道；更新前看变更，别一键全更；备份和回滚做成日常。

## 写在最后

Cloudflare 那句话我认同：插件和注册中心的安全，应该写进代码，而不是靠信任某个权威或一份行为准则。

这句话对独立博客尤其成立。我们没有安全团队，没有渗透测试预算，唯一的资产是几百篇文章和一点读者信任。在这种条件下，**默认不给权限、出了事能回滚**，比「这个插件很出名所以应该没事」可靠得多。

WordPress 不会因为 EmDash 消失，但下一个十年，插件该不该和我共用同一个进程，答案大概会变。
