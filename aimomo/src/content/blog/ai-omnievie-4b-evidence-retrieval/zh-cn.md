这两天模型圈的消息挺密：混元把翻译底层切到 Hy-MT3、英伟达开源 Nemotron 生图模型、蚂蚁百灵放了设计生图权重。但我最想拿出来讲的是 11 月 28 日前后腾讯 IMA 产品中心和优图实验室开源的 OmniEVIE-4B，因为它是这堆发布里少数真正在改"检索这件事怎么交付结果"的东西。

## 一、先看它到底给了什么

4.54B 参数，Qwen3.5 骨干，Apache-2.0，权重在 Hugging Face，代码和 CLI 在 GitHub 上。

它一个 checkpoint 同时支持两种检索模式：

- **Full 模式**：每个 token 保留 2048 维原样，不压缩，MMEB 总榜 60.68；
- **Compressed 模式**：把一页文档、一张图、一段视频压到最多 128 个 64 维 int8 向量，单条记录不超过 9,472 字节，100 万条记录占 8.82GiB，分数只掉到 60.06。

掉的这 0.62 分换来的东西很实在：100 万条记录，单 CPU 线程 54.2ms 查完（14.6ms 粗筛 + 19.7ms 汉明距离 + 19.9ms int8 精排）；500 万条 120.2ms。K 降到 32，100 万条的索引还能压到 2.15GiB。

官方给的榜单是 MMEB（2026-11-24 快照），排除音频后 190 个任务里排第一，视觉文档 84.70、文本 52.97、Agent 54.14。这里必须说清楚：这份成绩是团队自己复现提交的，榜单是第三方维护，但分数不等于你的场景就好用，只能当作"它有能力"的信号。

## 二、我认为最有意思的不是速度，是"证据定位"

过去我们用向量检索，命中的交付物一般是一段文本摘要或者一个文件路径。你得自己再翻一遍原文去核对，所以 RAG 系统里最贵的一步往往是"人回头验证"。

OmniEVIE 把这个动作内建了：每次命中都自带坐标。文档是页面上的 bounding box，视频是时间区间和峰值时间戳，都是直接从压缩索引的 `argmax` 出来的，不需要外挂 OCR，也不需要视频字幕模型。

它给的实测数字在 QVHighlights 验证集 1,083 条查询上：峰值落在标注区间内的占 78.0%，返回区间与标注区间有交集的占 94.3%（随机基线 44.9%），平均覆盖 18% 的时长。

我理解这三个数字的关系是这样的：94.3% 说明它"基本不会指错地方"，78.0% 说明它"能精准指出中心在哪"，而 18% 说明它给的是一个足够窄的候选范围，不是把整段视频丢回给你。最后这个数字最实用——五分钟的视频里定位到 54 秒左右，人眼扫一遍就能确认。

文本、图片、视觉文档、原生视频、Agent 的 GUI 轨迹和记忆，走的是同一套时空引导聚类（ST-HAC）。位置编码只参与分组，存下来的质心是纯语义的，所以同一份索引里，找一段文字和找一段视频动作是一回事。

## 三、对做站的人意味着什么

我第一反应是站内搜索。

现在的静态站站内搜索基本是 Pagefind 那种关键词索引，快、免费、零后端，但它只能告诉你"这几篇文章里有这个词"。你没法问"哪张图的哪一块讲了这件事"，也没法问"这条视频第几秒在说这个"。

这种模型给了另一条路：先把站里的图片、视频、PDF 都编成向量，用户搜一句自然语言，直接跳到段落位置。代价也真实——你得跑一次推理，4.5B 模型要 flash-attn 2.7 以上，权重也不是小文件，托管在纯静态平台上做不了，得有一台常驻机器或者一个 Worker + 推理服务。

另一个坑官方自己在 README 里写了：**每个输入要走单独的 forward pass**，因为 padding 会改变线性注意力层的循环状态。这句话看着是技术细节，实际意思是批处理不好做，吞吐会比你想的低。

## 四、我的判断

检索模型这个赛道，过去一年卷的是榜单分数，现在开始卷"压缩比"和"证据粒度"。OmniEVIE 的思路是：把索引压到能塞进一台小机器，同时保留"指给你看"的能力。前者决定小团队用不用得起，后者决定检索结果能不能被信任。

但我还是那句老话：基准分数是厂商自评的，端到端体验是另一件事。企业搜索里真正的难题往往不在召回，而在权限、增量更新、以及"命中了十份相似文档该信哪一份"。这个模型解决的是其中一层，不是全部。

值得试，但别把关键判断一次性交出去。
