WordPress 在 2026 年 11 月 18 日发布了 7.1.5，一次性处理 WordPress Core 里 20 个安全问题，官方建议立即更新。

## 一、这次修的都是什么

最受关注的是一处 Template Part 区块缺陷，由研究员 Logan Homolka 报告。Template Part 就是页眉、页脚这类共享布局元素用的区块。缺陷允许未认证攻击者取得本不该拥有的权限，并可能导向远程代码执行（RCE）。

公告里有两个"没写"要注意：没有报告已有在野利用，也没有指明哪些站点配置会允许代码执行。前者是好消息，后者意味着你没法判断自己在不在风险范围内。这种情况下稳妥的做法只有一个，当它已经被打。

其余几处：一个多站点问题，由 Yuval Miller 报告，某个站点的管理员可能借此接管 SuperAdmin 账号；两处 SQL 注入，分别在 WP_Meta_Query（Christiaan Swiers 报告）和 Customizer 首页预览（Rudy Faile 报告）；若干 XSS，其中一处存储型 XSS 影响评论功能且不需要账号，其余覆盖旧版媒体库、嵌入内容与区块编辑器；未登录状态下通过 REST API 搜索会暴露私有分类项，包括分类目录和标签；再加上 XML-RPC pingback 拒绝服务和评论编辑权限绕过。

20 条里还有两项预防性改动：更严格的 JSON 内容类型检查，以及移除已停服的 Imgur 嵌入选项。

## 二、攻击面正在往核心的区块编辑器迁移

这点我认为比单个漏洞更重要。

以前说 WordPress 不安全，大家第一反应是插件装太多。这次 20 个里有相当一部分落在区块编辑器、Template Part、REST API 上，而且是未认证就能触发的类型。这是个趋势：区块编辑器承担越来越多渲染和权限判断的职责，已经成了正经的攻击面，复杂度不比插件低。

对站长来说，"我只装了一个插件、很干净"不再等于安全，核心本身就要保持更新，而且要优先。

## 三、自动更新到底开不开

我的答案是小站开、大站看情况，但都要能验证。

自动更新最大的价值是缩短暴露窗口。这次这种未认证就能打的缺陷，你晚三天更新，就是三天敞着门。对个人博客来说，被塞垃圾链接，损失远大于一次更新可能带来的小兼容问题。

开了之后要验证。我的做法是更新完去后台看一眼版本号确实是 7.1.5，再打开首页和文章页确认布局没崩，最后看前台评论区是否正常。版本号不对，说明自动更新根本没跑成，常见原因是文件权限或维护模式卡住。

大站可以核心自动、插件手动，更新前留一份快照。

## 四、旧分支的补丁是缓冲期，不是长期方案

这次同步打了补丁的旧分支是 7.0.9、6.9.12 和 4.7.40。WordPress 4.6 及更早的版本不再接收安全更新。

要说清 4.7.40 这类版本的性质：它是给暂时升不上去的站点留的缓冲期。可能你有个老主题依赖旧接口，或者主机 PHP 太老跑不了新版，补丁能救命。但缓冲期不是长期方案，旧分支只打关键补丁，不跟进安全架构改造，而且迟早会停。

至于 7.2：RC2 已经包含这些修复，正式版计划 12 月 8 日发布。但别等，现在这个 7.1.5 该上就上。

## 五、给个人站长的升级顺序

我的顺序是：先把核心更新到 7.1.5，再看插件有没有兼容提示，然后核对版本号，最后做一轮站点自检——首页、文章页、后台登录、评论提交、REST 接口能不能正常返回。

核心放前面，是因为这次修的是未认证即可触发的洞，风险敞口不同，顺序就该不同。

最后是我的判断：这次更新真正提醒人的不是"20 个漏洞"这个数字，而是核心组件的复杂度已经上来了。插件选得再克制，核心版本落后一样是裸奔。把更新当日常、把版本号核对当习惯，比研究每个 CVE 的细节更实际。
